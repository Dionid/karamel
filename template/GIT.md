# Git — процедуры

Детали, вынесенные из [`AGENTS.md`](AGENTS.md). Там остались правила, которые
обязаны сработать без обращения к справочнику; здесь — почему они такие, точные
команды и скиллы, которые вызываются, когда возникла их ситуация.

## Почему PR всегда Draft

Готова работа к мержу или нет — решает человек. Снятие draft такое же чужое
действие, как апрув и мерж, и зелёный пайплайн его не разрешает. Ready-режима у
`commit-and-mr` нет вообще: `gh pr create` всегда получает `--draft`, а `gh pr edit` из этого
скилла статус не меняет.

## Почему PR не открывается без описания

Заголовок PR — это subject первого коммита, а ветка живёт дольше него.
Описание — единственное место, где ревьюер и следующий агент узнают, зачем PR,
что в нём по фичам, что трогает инфраструктуру и как это проверено. Пустое или
однострочное описание не выглядит поломкой, поэтому правило держит скрипт, а не
память агента: `commit-and-mr/run.sh` открывает PR только с
`--mr-description-file`, прошедшим проверку по
[`mr-description/template.md`](agents/common/skills/mr-description/template.md),
и отказывает до коммита. Ход по уже открытому PR идёт с `--existing-mr`: он
пушит, находит тот же PR через `gh pr list` и никогда не открывает новый;
вместе с `--mr-description-file` он заменяет описание этого PR, а с
`--description-only` — только описание, без коммита и push. Если gh не смог
перечислить PR ветки, новый PR не открывается ни в каком режиме
(`MR_STATE=unconfirmed`).

## Задача из нескольких PR

Как только одна задача заканчивается больше чем одним pull request —
несколько репозиториев, спека рядом с кодом — итоговый отчёт обязан назвать:

1. **автора** — git-идентичность коммитов ветки плюс агента из трейлера
   `Co-Authored-By`;
2. **ссылки на все PR этой задачи и порядок их merge**.

Cross-link `commit-and-mr` ставит сам: после каждого открытого или найденного
PR `task-link.sh --update` через gh переписывает блок задачи во всех открытых
PR, так что ранние PR узнают о поздних. Сбой этого шага — предупреждение с
командой повтора; перенесите его в отчёт.

## GitHub и единый токен

Все Git-операции идут по HTTPS через общую библиотеку `commit-and-mr`.
Единственный источник аутентификации — `GITHUB_TOKEN`: сначала окружение
процесса (включая явно пустое значение), затем корневой `.env`. Другие
переменные токенов и сохранённый логин CLI не переопределяют этот выбор.
`GH_TOKEN`, keyring и SSH не используются. Библиотека передаёт тот же
токен в `gh` и git, не печатая его.

Нет токена, токен отклонён или `gh` недоступен — операция останавливается до
коммита и push. Выполните skill [`github-login`](agents/common/skills/github-login/SKILL.md),
настройте `GITHUB_TOKEN` и повторите исходную команду. Сетевая ошибка также
останавливает доставку. Переключения транспорта нет.

## Починка существующего PR — на его же ветке

Дубликат появляется ровно одним способом: из привычки завести свежую ветку.
Поэтому до первого коммита поставьте чекаут на ветку PR и убедитесь в этом:

```bash
.claude/skills/wt/adopt.sh <source_branch> --repo <repo>
git -C worktrees/<task>/<repo> branch --show-current   # должно напечатать ветку PR
```

`commit-and-mr` с `--existing-mr` тогда вернёт `MR_STATE=existing` с той же
ссылкой.

## Скиллы вокруг PR

- **Ожидание пайплайна** — отдельного скилла для этого нет. Состояние PR, checks и
  комментарии ревью по просьбе читает child через общий GitHub transport
  (`gh pr view <ветка> -R <origin>`, `gh pr checks <ветка> -R <origin>`).
  Повторяющаяся проверка — только Cron Job рантайма с подтверждением
  человека, см. «Расписания» в [`AGENTS.md`](AGENTS.md#расписания).
- **Красный или отревьюенный PR** — пользователь приносит pipeline trace и
  review comments; исправление идёт на source branch через
  `systematic-debugging` и `receiving-code-review`.
