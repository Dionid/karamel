# Worktree — `wt`

`wt` управляет git-worktree для **любого** репозитория из `packages/`, чтобы
параллельные задачи не мешали друг другу. Каждый worktree — отдельный чекаут на
своей ветке (`<branchPrefix><task>`), делящий с репозиторием одно хранилище
`.git`.

```text
<workspace>/
├── .claude/skills/wt/wt      # скрипт, рядом со скиллом, который его документирует
├── .claude/skills/clone/clone.sh
├── harness.json              # корневой маркер: по нему скрипты находят воркспейс
├── repos.json                # манифест: какие репозитории есть и откуда
├── packages/                 # сами репозитории — каждый ровно один раз (gitignore)
│   └── <repo>/
├── worktrees/                # ничего, кроме worktree                  (gitignore)
│   └── <task>/               # один каталог на задачу → ветка <branchPrefix><task>
│       ├── <repo>/
│       └── <other-repo>/
└── .coordination/            # локальные leases, handoff и PR state    (gitignore)
```

Ни `packages/`, ни `worktrees/` этот репозиторий не трекает — см.
[Манифест](#манифест--reposjson).

`repos.json.always` добавляет настроенные обязательные репозитории к каждой
задаче. По умолчанию список пуст. Пути знаний и спецификаций определяются
полями `knowledgeRoot` и `specRoot`, без встроенных корпоративных адресов.
`knowledgeRoot: "."` размещает категории знаний в корне репозитория; без поля
сохраняется каталог `knowledge/`.

## Как вызывать

**Никакого `./wt` в корне нет.** Скрипт живёт в своём скилле, и этот путь —
точка входа. Воркспейс он находит, поднимаясь до `harness.json`, поэтому
работает из любого cwd, как и любой алиас или симлинк на него:

```bash
.claude/skills/wt/wt list                        # из корня воркспейса
../../.claude/skills/wt/wt list                  # изнутри packages/<repo>
alias wt=~/workspace/.claude/skills/wt/wt        # в своём shell rc
```

**Примеры ниже написаны как `wt …`** — заведите алиас или подставьте полный
путь. У агентов алиаса нет: `AGENTS.md` и скилл `wt` пишут путь целиком, и в
любом тексте, который выполняет агент, его тоже надо писать целиком.

Раскладка — **сначала задача, потом репозиторий**. Задача, охватывающая
несколько репозиториев, кладёт их все под один `worktrees/<task>/`: вся её
поверхность — одно дерево для поиска и один `cd`.

Worktree лежат в **отдельном верхнеуровневом `worktrees/`**, никогда внутри
репозитория и никогда внутри `packages/`. Причин две: вложенные чекауты ломают
globbing воркспейсов, tsconfig и обход eslint; а `packages/` остаётся
«одна копия на репозиторий», так что grep или агент, ищущий там, не может
попасть в тот же файл на трёх ветках и отредактировать не ту копию.

Все репозитории задачи носят одно имя ветки, но каждая ветка — в своём
репозитории: создаются, коммитятся и пушатся они независимо.

## `packages/` обязан быть свежим — `wt new` это проверяет

`packages/<repo>` — это и точка ветвления, и источник `.env*`, `.husky/_` и
`node_modules` для нового worktree. Устаревший чекаут означает и устаревший
старт, и устаревшие зависимости/служебные файлы хуков, поэтому `wt new`
отказывается его использовать:

```console
$ wt new fix-rounding --repo api
[api] packages/api is 12 commit(s) behind origin/development
  it is the branch point AND the source of the worktree's .env*/node_modules/.husky/_
    git -C packages/api pull   (or: --pull to do it here, --allow-stale to ignore)
```

```bash
wt new fix-rounding --repo api --pull      # фастфорвардить здесь же
git -C packages/api pull && wt new …       # то же самое руками
wt new … --allow-stale                     # ветвиться от origin/<base>, приняв старые зависимости
```

`--pull` делает `git merge --ff-only origin/<base>` в главном чекауте, то есть
никогда ничего не переписывает и не мержит: если там локальные коммиты, грязное
дерево или другая ветка — `wt` скажет об этом и не тронет. Для задачи из
нескольких репозиториев проверка идёт по каждому: свежие создаются, отставшие
попадают в `failed:`.

Fetch `origin/<base>` (как и clone, `adopt.sh` и `wt pull`) идёт через
`commit-and-mr/lib.sh`: HTTPS и единый `GITHUB_TOKEN` из окружения процесса
или корневого `.env`, с приоритетом окружения. Нет токена или доступ отклонён —
команда печатает причину и `NEXT=github-login`. Сетевая ошибка допускает
локальный ref только там, где это явно разрешено флагами команды; отказ
аутентификации не маскируется как offline.

### `wt pull` — тот же фастфорвард, но для чтения

```bash
wt pull --repo api                # или просто: wt pull api web
wt pull                           # репозиторий, в котором находится cwd
wt pull all                       # все из манифеста — медленно, редко нужно
wt pull --repo api --no-fetch     # сравнить с последним известным origin/<base>
```

Ответ, полученный из отставшего дерева, выглядит ровно так же, как правильный, —
поэтому чтение кода начинается с `pull`. Отказы те же (грязное дерево, локальные
коммиты, другая ветка), докладываются по каждому репозиторию и не обходятся.
**Ненулевой код возврата**, если хоть один остался позади, — частичный pull
нельзя принять за выполненный.

`worktrees/` он не трогает никогда: worktree сидит на своей ветке, где
`origin/<base>` — не то, что стоит вливать. Такой чекаут обновляется через
`git -C worktrees/<task>/<repo> pull --ff-only`.

## Команды

```bash
wt repos                                       # что лежит на диске: ветка + origin
wt new   <task> [--repo <name>]... [--base <b>] [флаги зависимостей]
wt list  [--repo <name>]...                    # задачи + coordination, либо сырой repo view
wt rm    <task> [--repo <name>]... [--force] [--delete-branch]
wt prune [--repo <name>]...
wt cleanup [<task>]... [--dry-run] [--no-fetch]  # удалить задачи, уже вошедшие в base
wt pull  [<name>|--repo <name>]... | all       # фастфорвард packages/ до origin
wt seed  [<name>|--repo <name>]... | all       # node_modules в packages/ (один раз на репо)
wt doctor [--repo <name>]... [--no-fetch]      # здоровье раскладки
wt clone [<name>...] [--install]               # пересоздать packages/ из манифеста
wt clone-url <task> <git-url> [--name <name>] [--task-branch]  # разовый checkout
wt manifest                                    # пересобрать repos.json из packages/
```

- `--repo` — имя каталога в `packages/`, **повторяемо**:
  `--repo api --repo web` работает с обоими.
- Без `--repo` умолчание разное:
  - `new` — репозиторий, в котором лежит cwd. Автоопределение работает изнутри
    `packages/<repo>/…` и `worktrees/<task>/<repo>/…`, но **не** из корня и не
    из самого `worktrees/<task>/`;
  - `rm` — **все репозитории задачи**; работать, пока shell внутри
    `worktrees/<task>/`, он откажется;
  - `prune` — все репозитории `packages/`;
  - `list` — вид по задачам; с `--repo` — сырой `git worktree list`.
- `--base` переопределяет точку старта. Без него берётся `branch` репозитория из
  манифеста, а если его нет — `origin/HEAD`.

```bash
# один репозиторий, попутно обновив главный чекаут
wt new fix-rounding --repo api
#   -> worktrees/fix-rounding/api

# задача на три репозитория — одна команда, один каталог
wt new drop-promo --repo shared-lib --repo api --repo web
#   -> worktrees/drop-promo/{shared-lib,api,web}

# автоопределение по cwd
cd packages/web && wt new spike-ui
```

Упавший репозиторий не отменяет остальные: `wt new` печатает `created:` и
`failed:` и завершается ненулевым кодом, если что-то не вышло.

### Репозитории из `always`

У манифеста есть верхнеуровневый список `always`, и каждый репозиторий из него
входит в **каждый** `wt new` поверх запрошенных:

```json
{ "always": ["spec-repo"] }
```

```bash
wt new fix-rounding --repo api
#   -> worktrees/fix-rounding/{api,spec-repo}
```

Так репозиторий спек (или любой другой, нужный каждой задаче) оказывается в
дереве каждой задачи, на той же ветке, что и код, — спека и реализация едут
вместе. Назвать его явно безвредно — он
добавится один раз. `--no-always` отключает, а репозиторий из `always`, которого
нет в `packages/`, пропускается с предупреждением, а не валит запуск.

### Ленивое клонирование — `ensure-repository`

Если явно запрошенный для `wt new` репозиторий есть в `repos.json`, но его ещё
нет в `packages/`, `wt` сначала лениво вызывает
`.claude/skills/clone/ensure-repository`. Эта primitive берёт per-repo lock,
клонирует во временный каталог на том же filesystem, проверяет token-free
`origin`, запускает `git fsck` и только потом атомарно переименовывает candidate
в `packages/<repo>`. Частичный checkout не используется — половина репозитория,
появившаяся из-за прерванного клона, выглядит как рабочий чекаут и ломается
позже и не там.

`.claude/skills/clone/clone.sh --always` клонирует только репозитории из списка
`always`; запуск без имён остаётся явным ручным clone-all режимом.

### Продолжить существующую ветку — `adopt.sh`

`wt new` всегда *создаёт* ветку, что неверно, когда ветка уже на origin (раунд
ревью на чужой ветке, часть серии, запушенная с другой машины): он форкнет
вторую ветку под тем же именем. Этот случай —
[`.claude/skills/wt/adopt.sh`](agents/common/skills/wt/adopt.sh), он же
`make adopt`:

```bash
.claude/skills/wt/adopt.sh feature/withdraw-flow/03-wallets --repo api
make adopt BRANCH=feature/withdraw-flow/03-wallets REPO=api
#   -> worktrees/withdraw-flow/03-wallets/api, ровно на этой ветке
```

Имя задачи — всё, что идёт после префикса, поэтому раскладка не меняется и
`wt list`/`rm`/`doctor` не видят ничего особенного. Обёртка добавляет три вещи,
без которых `wt new` тут просто не запустится:

- **чистит мёртвые регистрации** — ветка, чей каталог удалили руками, всё ещё
  считается «вычекаученной», и до неё не добраться, пока не прошёл `prune`;
- **удаляет локальные ветки, чьё *имя* блокирует новую.** Git хранит рефы
  файлами, поэтому `refs/heads/feature/x` и `refs/heads/feature/x/03` не могут
  сосуществовать. Блокирующая ветка удаляется только после доказательства, что
  она уже содержится в origin-рефе, и её sha печатается первым —
  `--drop-unmerged` снимает отказ, а напечатанный sha это путь назад. Ветки
  *ниже* по имени не трогаются никогда: скрипт отказывается и перечисляет их;
- **запускает `wt new --base <branch> --allow-stale --no-always`.** `--base`
  делает старт на удалённой ветке (и даёт этот реф как upstream); `--allow-stale`
  неизбежен, потому что `packages/<repo>` сидит на своей базовой ветке и «отстаёт»
  по определению — так что настоящая устарелость главного чекаута проверяется и
  докладывается отдельно; `--no-always` не даёт запуску упасть на репозитории из
  `always`, который эту ветку обычно не носит.

Повторный запуск — no-op, если worktree уже есть, и пересоздание чекаута из
origin, если каталог удалили, а локальная ветка осталась. `--dry-run` печатает
все шаги и ничего не трогает.

**Одна задача — несколько веток одного репозитория.** Каждая ветка
`<branchPrefix><task>/<sub>` получает свой worktree
`worktrees/<task>/<sub>/<repo>` и свой MR, а `coord claim`/`finish` идут по
внешнему `<task>`. Такую ветку ставит `adopt.sh`. Голой ветки
`<branchPrefix><task>` рядом быть не должно: git не держит `x` и `x/<sub>`
одновременно (см. второй пункт выше). Как адресовать и удалять такие
чекауты — в [Удалении](#удаление).

### Удаление

`wt rm` сначала спрашивает coordination registry и отказывается удалять задачу
с живой lease. Сам `wt` состояние PR не проверяет: сначала подтвердите, что
PR смёржен или закрыт — человек в UI или child одним чтением
`gh pr view <ветка> -R <origin> --json state,body` (поле `state`), — затем в чистом
checkout проверьте `git status` и отсутствие незапушенных коммитов. После
этого:

```bash
.claude/skills/coordination/coord release <task>
.claude/skills/wt/wt rm <task> --repo <repo>
```

`wt rm` не передаёт `--force` и сохраняет локальные ветки. Он проверяет живых
владельцев и dirty state, но не доказывает состояние PR или его source SHA —
эта часть остаётся явной проверкой до вызова; архивные `cleanup-merged-task` и
`cleanup-worktrees`, которые делали её автоматически, не восстановлены.

Задачи, чья работа уже лежит в целевой ветке, убирает `wt cleanup`. Он
делает fetch `origin/<base>` каждого репозитория и удаляет задачу вместе с
ветками `feature/<task>`, только если **каждый** её checkout:

- чист и стоит на своей ветке — не detached, без незавершённых rebase, merge
  или bisect;
- не держит игнорируемых файлов, кроме пересобираемых (`node_modules`, `dist`,
  `build`, кэши, symlink-и `.env*`);
- имеет HEAD в `origin/<base>`: как предок (merge, fast-forward) или теми же
  патчами (rebase, cherry-pick — `git cherry`).

Хотя бы один checkout задачи должен был что-то закоммитить: свежая задача без
коммитов не «завершена». Задачу с живой lease и задачу, внутри которой стоит
shell, он не трогает; вложенные задачи (`worktrees/<task>/<sub>/`) судятся по
отдельности. Squash-merge нескольких коммитов оставляет в base другой патч,
поэтому такая задача остаётся с причиной в отчёте — её удаляют `wt rm` после
проверки PR глазами. Сначала `--dry-run` и показ списка человеку, потом запуск.

**Bookkeeping `agent-directed-routing`.** `worktrees/<task>/.agent-routing/`
(у вложенной задачи — `worktrees/<task>/<sub>/.agent-routing/`) — не задача и не
репозиторий: `list`, `doctor` и `cleanup` его не сканируют, а имя задачи с
компонентом `.agent-routing` `wt` отвергает. Задачу удерживает «работа идёт»
в любом таком каталоге на её пути или ниже: непустой `checkouts/`, запись
ledger `ownership.json` не в `integrated`/`failed` (то есть
`reserved`/`active`/`patch_ready`), нечитаемый ledger, файлы в `recovery/` или
`journals/`. Тогда `cleanup` оставляет задачу с причиной, а `wt rm` отказывает;
`--force` (только человек) удаляет и это bookkeeping — writer-checkout'ы с их
регистрацией в git, ledger и recovery-bundles. Когда у каталога задачи не остаётся checkout'ов, `wt rm` убирает и
простаивающий `.agent-routing/`, иначе он навсегда держал бы каталог.

```bash
wt cleanup --dry-run      # что уйдёт и почему остальное остаётся
wt cleanup                # все задачи в worktrees/
wt cleanup fix-rounding   # только названные
```

```bash
wt rm drop-promo --delete-branch                  # все три, каталог задачи уходит
wt rm drop-promo --repo web --delete-branch       # только один, каталог остаётся
```

`--repo` разрешается по чекаутам, которые у задачи реально есть, а не по
`worktrees/<task>/<repo>`, поэтому одинаково работает и на вложенной задаче —
раскладке, которую создаёт `adopt.sh` для ветки `<branchPrefix><task>/<sub>`:

```bash
wt rm withdraw-flow --repo api            # найдёт 03-wallets/api
wt rm offramp --repo api                  # откажется: подходит 4 чекаута
wt rm offramp --repo 04-reserve/api       # подпуть выбирает один
```

**Вложенное имя задачи вкладывает и каталог.** `wt list`, `rm` и `doctor`
находят чекауты по их записи `.git` на любой глубине, а не предполагают
`worktrees/<task>/<repo>`. Адресуйте такую задачу полным именем —
`wt rm withdraw-flow/03-wallets`, — и пустые группирующие каталоги уйдут вместе
с ней.

> Клонированный (или залинкованный) `node_modules` не трекается, поэтому такому
> worktree для удаления нужен `--force`.

## `wt doctor` — здоровье раскладки

```bash
wt doctor                    # все репозитории и все worktree
wt doctor --repo api         # сузить обе секции
wt doctor --no-fetch         # без fetch по каждому репозиторию (офлайн, спешка)
```

Фетчит базовую ветку каждого репозитория и докладывает — **выход 1** на
проблеме, предупреждение на заметке:

| Сообщение | Почему важно | Что делать |
| --- | --- | --- |
| `N commit(s) behind origin/<base>` | проблема — `wt new` откажется, а ответ по этому дереву будет устаревшим | `wt pull --repo <repo>` |
| `in repos.json but not on disk` | проблема — `--repo <name>` не разрешится | `wt clone <name>` |
| `broken symlink: <path>` | проблема — цель `.env`/`node_modules` исчезла из `packages/<repo>` | перелинковать или переустановить в главном чекауте |
| `missing .env…` | заметка — файл добавили в `packages/<repo>` после создания worktree | `ln -s`, который он печатает |
| `N stale worktree registration(s)` | заметка — каталоги удалили руками, а не через `wt rm` | `wt prune --repo <name>` |
| `checkout sits on '<branch>'` | заметка — не базовая ветка, `--pull` не сможет фастфорвардить | вернуть на базу или игнорировать |
| `no node_modules in packages/<repo>` | заметка — клонировать нечего, следующий `wt new` поставит их в `packages/<repo>` (минуты) и склонирует оттуда | ничего, либо `wt seed --repo <repo>` заранее |

Две проверки симлинков — самые полезные в ежедневной работе: появившийся на
прошлой неделе вложенный `.env` или ссылка `node_modules`, указывающая на
переустановленный `packages/<repo>`, изнутри worktree выглядят в точности как
ошибка в коде.

## Манифест — `repos.json`

`packages/` в gitignore, поэтому клон воркспейса даёт `wt`, доки и конфигурацию —
и больше ничего. Источник истины о том, что должно лежать в `packages/`, —
`repos.json` в корне этого репозитория:

Создание и изменение манифеста ведёт skill
[`repos-manifest`](agents/common/skills/repos-manifest/SKILL.md).
Полная схема, типы, defaults и потребители всех полей — в его
[справочнике](agents/common/skills/repos-manifest/schema.md).

У подключённого через `skills` скилла два молчаливых следствия: он читается с дефолтной ветки
`packages/<repo>/`, так что правка в `worktrees/<task>/<repo>/` живой не
становится до мержа; а воркспейс с непополненным `packages/` скилла не имеет
вовсе — `./ops sync` только предупредит и продолжит, в список скилл не попадёт.

```bash
git clone <team-repo-url> workspace && cd workspace
./ops setup                             # собрать runtime-деревья агента
export NPM_TOKEN=…                   # приватные registry
wt clone                             # склонировать все репозитории манифеста
wt clone api web                     # …или только некоторые
wt clone --install                   # ещё и поставить зависимости в главных чекаутах
```

`wt clone` пропускает уже существующие, так что его безопасно перезапускать
после добавления репозитория. Ставить зависимости по умолчанию он **не** будет —
десяток деревьев `node_modules` это ожидание, которое лучше контролировать.

Хуки запускаются с cwd в целевом каталоге и получают в окружении
`ROOT_WORKTREE_PATH` (главный чекаут) и `REPO_NAME`; `wt` также задаёт `WT_DIR`,
а `clone.sh` — нет.

Добавив репозиторий в `packages/` руками, запустите `wt manifest` — он обновит
`url` из чекаутов и добавит новые записи, сохранив остальные поля и существующую
непустую `branch`; расхождение с remote default выдаст предупреждение.
Команда пишет манифест найденного workspace-root: правку запускайте в task-worktree,
а не в корневом checkout. `wt repos` предупреждает о записях
манифеста, для которых нет каталога на диске.

## `.env`, `.husky` и `node_modules`

`node_modules`, настоящие `.env*` и установленный каталог Husky `.husky/_` в
gitignore, поэтому git их не переносит.

**`.env` — симлинками, включая вложенные.** `wt new` находит каждый
gitignore-нутый `.env*` в репозитории и симлинкует его в worktree по тому же
относительному пути. Трекаемые шаблоны (`.env.example`, `.env.sample`) не
трогаются — они и так в чекауте. Один источник истины: правите файл в
`packages/<repo>/`, и его видят все worktree.

- `--copy-env` — копировать, а не симлинковать (независимо на worktree).
- `--no-env` — не переносить `.env*` вообще.

**`.husky/_` — копией.** `wt new` переносит из `packages/<repo>` только
gitignored support-dir `.husky/_`, если он есть. Tracked hook-файлы вроде
`.husky/pre-commit` остаются из самой ветки worktree, поэтому локальная копия не
затирает изменения hook entrypoints в задаче.

**`node_modules` — copy-on-write клон, и это умолчание.** Поле `deps` решает по
репозиторию, флаги переопределяют на один запуск.

| Стратегия | Что делает | Цена | Может ли worktree держать свои версии? |
| --- | --- | --- | --- |
| `clone-modules` **(по умолчанию)** | `cp -Rc` — copy-on-write клон каждого `node_modules` из `packages/<repo>` | секунды, только метаданные | **да** — дерево принадлежит worktree |
| `install` | установка с нуля определённым пакетным менеджером (`bun install`, `npm ci`, `pnpm install --frozen-lockfile`, `yarn install --frozen-lockfile`) | минуты, полная копия на worktree | да |
| `link-modules` | симлинки на каждый `node_modules` репозитория | мгновенно, 0 диска | **нет** — общий каталог |
| `none` | ничего | — | — |

**Почему по умолчанию клон.** Worktree, разделяющий `node_modules` с
`packages/<repo>`, не может поменять версию зависимости — правка задела бы все
остальные worktree и главный чекаут. Worktree, установленный с нуля, может, но
платит минутами и гигабайтом. Клон даёт и то и другое: `npm install <pkg>@<ver>`
внутри клонированного worktree — это **диффовая установка** в секунды, и
переписывает она только файлы этого worktree, потому что copy-on-write рвёт
общие блоки на первой же записи.

Два следствия:

- **В worktree используйте `npm install`, а не `npm ci`.** `ci` удаляет
  `node_modules` и пересобирает из lock-файла, то есть выбрасывает клон и платит
  полную установку.
- **Монорепо на воркспейсах работают.** npm заводит воркспейсы *относительными*
  симлинками (`node_modules/@scope/main -> ../../app`), клон копирует их
  симлинками — то есть внутри worktree они разрешаются в **его собственные**
  исходники. Это ровно та ловушка, которая есть у `link-modules` и которой нет у
  клона.

**Полная установка — одна на репозиторий, а не одна на задачу.** Предусловие
`clone-modules` и `link-modules` — `node_modules` в **главном** чекауте. Когда
его нет, `clone-modules` ставит зависимости **в `packages/<repo>`** и клонирует
уже оттуда: следующий `wt new` по этому репозиторию — секунды. Установка внутри
worktree выглядела бы так же, но оставила бы главный чекаут пустым, и каждая
следующая задача платила бы заново — поэтому её здесь нет.

```bash
wt seed [<name>|--repo <name>]... | all   # поставить node_modules в packages/
```

`wt seed` — та же установка по требованию: чтобы отдать минуты один раз вне
задачи (например, сразу после `wt clone`). Репозиторий, у которого
`node_modules` уже есть, **пропускается**, а не переустанавливается — `--force`
переопределяет. Установка сорсит корневой `.env`, потому что `.npmrc`
репозиториев авторизуют приватный registry через `${NPM_TOKEN}`.
`wt doctor` называет репозитории, которые ещё не засеяны.

## Важное

- **Свежий `packages/<repo>` — предусловие `wt new`**, и оно проверяется.
- Как только worktree создан, **все правки в нём** — никогда в `packages/<repo>/`.
  Это подпёрто правилом `permissions.deny` на `Edit(/packages/**)`.
- Ограничивайте поиск одним деревом: `worktrees/<task>/` во время задачи,
  `packages/` в остальное время.
- Одно имя задачи → один `worktrees/<task>/`. Переиспользуйте `<task>` для всех
  репозиториев задачи, а не выдумывайте имена по репозиториям.
- Чтобы работать прямо в репозитории, откройте сессию внутри `packages/<repo>/`.

Для самого workspace, которого нет в `repos.json`, используйте
`wt clone-url <task> <git-url> --name <repo> --task-branch`.
Флаг создаёт ветку `<branchPrefix><task>` (например, `codex/task`).
Существующий checkout переиспользуется только с тем же origin и чистым
рабочим деревом: из default/base branch создаётся task branch; уже нужная
ветка оставляется на месте. Чужая ветка, detached HEAD, изменённые файлы или
другой origin дают отказ без reset и переключения.
