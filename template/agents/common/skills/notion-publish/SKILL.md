# Публикация документации в Notion

Контент уходит на страницу, **которую назвал пользователь** — никогда не на
страницу, выбранную скиллом. Если не дан ни URL, ни id страницы — спросите,
не создавайте страницу и не ищите правдоподобную цель по воркспейсу.

`run.sh` (рядом с этим файлом) делает всю работу с API. `NOTION_TOKEN`
читается из корневого `.env` внутри скрипта, поэтому он не попадает в
транскрипт — не переписывайте `curl`-вызовы инлайн. Это тот же `NOTION_TOKEN`,
которым пользуется чтение (`.claude/skills/notion/`) — один токен на команду,
одна интеграция в Notion.

## Ход работы

1. **Запишите документ в файл** — `<scratchpad>/notion-<тема>.md`. Обычный
   markdown: заголовки, списки, таблицы, код в блоках, ссылки. Notion сам
   конвертирует.

   **Правила форматирования этого markdown**:
   - список всегда обрамлён пустой строкой до и после — никогда не приклеен
     прямо к заголовку или абзацу выше/ниже;
   - за каждым абзацем следует пустая строка перед тем, что идёт дальше.
2. **Проверьте целевую страницу — непосредственно перед каждым вызовом
   `publish`, не один раз в начале задачи.** Страница — общее внешнее
   состояние, не файл в репозитории: между любыми двумя вашими вызовами её
   мог поправить человек прямо в Notion. Если в рамках одной задачи это уже
   вторая, третья и так далее правка той же страницы — `check` запускается
   заново перед каждой из них, даже если страницу уже проверяли пять минут
   назад:

   ```bash
   .claude/skills/notion-publish/run.sh check "<page-url-or-id>"
   ```

   Печатает `PAGE_TITLE`, `PAGE_URL`, `EMPTY=yes|no`, и — если не пусто —
   `CHARS`, `EXISTING_FILE` и первые 40 строк того, что там есть.

   Если это не первая публикация в задаче — сравните то, что вернул свежий
   `check`, с тем, что вы сами туда положили прошлым вызовом. Совпадает —
   можно продолжать. Разошлось (другой `CHARS`, другой текст в начале) —
   стоп: кто-то поправил страницу в Notion между вашими вызовами. Покажите
   пользователю расхождение и спросите, что делать, вместо того чтобы
   перезаписать поверх — следующий шаг в любом случае не должен молча
   считать локальный файл-черновик единственным источником правды.
3. **Публикация — внешняя запись всегда, даже на пустую страницу.** Прежде
   чем звать `publish` в любом режиме, покажите пользователю: какая это
   страница (заголовок + url) и что именно на неё уйдёт (файл целиком или
   его краткое содержание) — и дождитесь согласия. Это тот же принцип
   движка, что и для любой другой внешней записи, а не специфика Notion; для
   пустой страницы согласие — не вопрос «Перезаписать?» (там нечего
   перезаписывать), а простое подтверждение цели и текста.

   Пустая страница, после согласия:

   ```bash
   .claude/skills/notion-publish/run.sh publish "<page-url-or-id>" --file <path>.md
   ```

4. **На странице уже есть контент** → **остановитесь и спросите пользователя,
   дословно:**

   > Перезаписать?

   В том же сообщении назовите, какая это страница (заголовок + url), сколько
   там уже есть и что это заменит, и предложите третий вариант — дописать в
   конец. Затем:

   - перезаписать → `publish … --file <path>.md --overwrite`
   - дописать     → `publish … --file <path>.md --append`
   - нет          → ничего не делать, доложить.

   Никогда не угадывайте ответ. `publish` без флага **отказывает** на
   непустой странице — это защита, а не проблема, которую нужно обойти.
5. **Доложите** возвращённый `PAGE_URL`, чтобы пользователь мог открыть
   страницу.

## Новая дочерняя страница вместо перезаписи существующей

Гипотеза, отчёт или заметка, которая относится *к разделу*, — это дочерняя
страница, а не переписывание страницы раздела. **Создание — тоже внешняя
запись и тоже ждёт согласия**: покажите пользователю родителя (заголовок +
url), заголовок новой страницы и её содержимое (или краткое содержание) —
и только после «да» зовите `create`:

```bash
.claude/skills/notion-publish/run.sh create "<parent-url-or-id>" \
  --title "<заголовок страницы>" --file <path>.md
```

Родитель сохраняет своё содержимое. `create` отказывает, когда у родителя уже
есть дочерняя страница с таким заголовком, и отказывает, когда markdown
родителя пришёл обрезанным API — частичный список детей прошёл бы проверку,
не увидев дубликат. `--allow-duplicate` снимает оба отказа. Печатает
`CREATED`, `PAGE_URL` и `PARENT_URL`.

**Если запись падает после того, как страница уже создана, она уходит в
корзину** — так титульный пустой огрызок не остаётся под родителем и не
блокирует повтор через защиту от дубликата. Единственный случай, который
нельзя убрать самому (вызов корзины тоже упал), докладывается с URL для
ручного удаления.

Вопрос о дубликате можно задать отдельно, до записи куда-либо ещё:

```bash
.claude/skills/notion-publish/run.sh has-child "<parent-url-or-id>" --title "<заголовок>"
```

`0` — дочерняя страница уже есть, `3` — её нет, что-либо ещё — вопрос не
удалось выяснить. Ничего не пишется в обоих случаях.

Пользователь по-прежнему называет родителя: `create` не выбирает страницу
сам, как и `publish`.

## Правила

- **`--overwrite` уничтожает текущее содержимое страницы.** Передавайте его
  только после того, как пользователь ответил на вопрос в этом же ходе.
  Согласие на одну страницу не распространяется на следующую.
- **Ни один `check` не действует дольше одного вызова `publish`.** Повторная
  правка той же страницы в рамках одной задачи — это снова шаг 2, снова
  свежий `check`, снова сверка с тем, что было опубликовано прошлым разом.
  Работа с ранее сохранённым локальным файлом-черновиком без повторного
  `check` перед каждой записью — это и есть сценарий, в котором чужая правка
  в Notion тихо исчезает под следующим `overwrite`.
- Публикация — внешнее действие: общая страница меняется для всех, кто её
  видит. Относитесь ко второй публикации на ту же страницу как к новому
  запросу.
- `--append` переписывает страницу из её собственного markdown-рендера плюс
  добавление. Всё, что markdown не может выразить (базы данных, synced
  blocks, embeds, кнопки), теряется в этом round-trip — если `check` показал
  такой контент, скажите об этом и дайте пользователю решить, а не дописывайте
  вслепую.
- Не придумывайте структуру, которую пользователь не просил. Просили
  changelog — публикуйте changelog, а не changelog с «Overview» и «Next
  steps» от себя.

## Настройка и отказы

`NOTION_TOKEN` — секрет внутренней интеграции (`ntn_…`) с
<https://www.notion.so/profile/integrations>. Добавьте его в корневой `.env` —
шаблон `env.example` перечисляет переменную. Нет значения — скажите об этом,
запасного пути нет:

```bash
.claude/skills/env-check/env-check.sh NOTION_TOKEN
```

- `NOTION_TOKEN is not set` — пользователю нужно добавить его в `.env`.
- `[unauthorized]` / 401 — токен неверный, отозван, или из другого воркспейса.
- `[object_not_found]` / 404 — почти всегда интеграция не подключена к
  странице. В Notion: меню страницы ⋯ → Connections → добавить интеграцию.
  Нужен доступ и к родителю, не только к дочерней странице.
- `[restricted_resource]` / 403 — у интеграции нет прав на чтение или
  обновление. Чинится в настройках интеграции, не в этом скилле.
- `TRUNCATED=true` у `check` — страница слишком велика для полного markdown
  API. Перезапись всё ещё безопасна; дописывание — отказ.

Скрипт принимает полный URL Notion, uuid с дефисами или голый 32-hex id и сам
нормализует его. `Notion-Version` зафиксирован в `run.sh` — там же его и
поднимайте, если API обновится.
