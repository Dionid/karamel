# Проверка кредов

`.env` читать нельзя: правило `permissions.deny` и хук на секреты отклоняют
прямое чтение файла, а любая форма вроде `${VAR:-…}` в bash напечатала бы
значение в транскрипт. `env-check.sh` — единственный способ узнать, вписал ли
человек токен, не увидев сам токен.

Запускается та копия скрипта, которая лежит **в корне воркспейса**:

```bash
<корень воркспейса>/.claude/skills/env-check/env-check.sh NOTION_TOKEN ASANA_TOKEN
```

Написание пути роли не играет: в корне `.claude/skills/env-check` — симлинк на
`agents/common/skills/env-check`, это один и тот же файл. Не играет роли и cwd:
корневая копия, запущенная из каталога worktree, отвечает правильно. Значение
имеет ровно одно — в каком чекауте лежит запускаемая копия (почему — в «Как это
работает»). Поэтому из worktree надёжен только абсолютный путь от корня
воркспейса, а скрипт, которому нужен кред, якорится на найденный им корень,
любым написанием:

```bash
ENV_CHECK="$ROOT/.claude/skills/env-check/env-check.sh"
[ -x "$ENV_CHECK" ] || ENV_CHECK="$ROOT/agents/common/skills/env-check/env-check.sh"
```

Три состояния на каждую переменную:

- `set` — значение есть и оно не совпадает с плейсхолдером шаблона;
- `missing` — переменной нет или она пустая;
- `placeholder` — значение дословно то же, что в `.env.example`: имя объявили,
  но не заполнили. Для гейта это то же самое, что `missing`.

Код возврата: `0`, если все запрошенные переменные `set`; `1`, если хоть одна
`missing` или `placeholder`. Значение не печатается ни в каком режиме и ни при
какой ошибке.

## Как читать вывод

Отвечает построчный `set`/`missing`/`placeholder`, а не код возврата: код —
AND по всему запрошенному списку. Спрашиваются каноничные имена из
`.env.example`: выдуманное имя честно получит `missing`.

Для GitHub проверяется только `GITHUB_TOKEN`. Окружение процесса имеет
приоритет над корневым `.env`, включая явно пустое значение. `set` доказывает
наличие токена, а доступ подтверждает общая библиотека `commit-and-mr` через
GitHub API с тем же токеном. Сохранённые credentials CLI не учитываются.

## Флаги

- `--from-example` — проверить все переменные из `.env.example` в корне
  репозитория, включая закомментированные (`# NOTION_TOKEN=…` в шаблоне значит
  «переменная опциональна», а не «такой не бывает»). Это инвентарь каноничных
  имён, а не гейт: в незаполненном окружении он почти всегда возвращает `1`.
- `--missing` — напечатать только незаполненные, для использования в гейте
  (`env-check.sh --missing NOTION_TOKEN || echo "нет токена"`).

## Как это работает

Корень репозитория ищется вверх по дереву **от каталога скрипта** по локальному
маркеру `harness.json` или, до первой сборки, по tracked-манифесту
`workspace.json`. Плейсхолдер вычисляется сверкой с `.env.example` в этом
корне — списком имён без значений, который трекается в git, а не по списку слов
вроде `your_`: список пришлось бы догонять при каждой новой интеграции.

Отсюда и требование про корневую копию. `agent-workspace` трекает `workspace.json`,
поэтому копия скрипта внутри `worktrees/<task>/agent-workspace/` объявляет корнем
сам worktree, где `.env` нет: предупреждение об этом уходит в stderr, а stdout
печатает обычные строки. Ложный `missing` получают при этом не все переменные,
а ровно те, которых нет в окружении процесса, — заданные только в корневом
`.env`.

Несекретные URL по умолчанию могут считаться заполненными при совпадении с
шаблоном. Секретные имена (`*TOKEN*`, `*KEY*`, `*SECRET*`, `*PASS*`,
`*CREDENTIAL*`, `*URI*`, `*DSN*`, `*DB_URL*`) исключением не пользуются:
URL-плейсхолдер у них всё равно `placeholder`.
