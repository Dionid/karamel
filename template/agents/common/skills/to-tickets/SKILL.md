# To Tickets

Разбить работу на **тикеты** — вертикальные tracer-bullet срезы, каждый со
своими **блокирующими** рёбрами (какие тикеты должны закрыться раньше).

## Процесс

### 1. Собрать контекст

Работать с тем, что уже есть в разговоре. Если пользователь дал ссылку (путь
к спеке, номер или URL issue) — прочитать её целиком.

### 2. Изучить код (по необходимости)

Если код ещё не изучен — прочитать нужные части, чтобы заголовки и описания
тикетов использовали словарь домена репозитория, а не выдуманный.

Искать возможности сначала прибраться в коде, чтобы имплементация стала
проще: «сделай изменение лёгким, потом сделай лёгкое изменение».

### 3. Черновик вертикальных срезов

<vertical-slice-rules>

- Каждый срез режет узкий, но ПОЛНЫЙ путь через все слои (схема, API, UI,
  тесты) — вертикально, а не горизонтальный слой одного уровня.
- Завершённый срез демонстрируем или проверяем сам по себе.
- Каждый срез помещается в одно свежее контекстное окно агента.
- Любая предварительная уборка кода делается первой.

</vertical-slice-rules>

Дать каждому тикету его **блокирующие рёбра** — тикеты, которые должны
завершиться раньше, чем этот сможет начаться. Тикет без блокеров может
стартовать сразу.

**Широкий рефакторинг — исключение из вертикальных срезов.** Широкий
рефакторинг — это одно механическое изменение (переименовать колонку,
перетипизировать общий символ), чей радиус поражения расходится по всей
кодовой базе: одна правка ломает тысячи мест разом, и ни один вертикальный
срез не проедет зелёным. Не впихивать его в tracer bullet — секвенировать как
expand–contract: сначала expand (добавить новую форму рядом со старой, ничего
не ломая), затем миграция вызывающих мест батчами по радиусу поражения
(пакет/каталог), каждый батч — свой тикет, заблокированный expand'ом, CI
остаётся зелёным от батча к батчу, потому что старая форма ещё жива; в конце
contract — удалить старую форму, когда не осталось вызывающих, тикет
заблокирован каждым батчем миграции. Если даже батчи не могут быть зелёными
поодиночке — держать последовательность, но пусть они делят интеграционную
ветку, которая блокирует финальный тикет «интегрировать и проверить»: зелёный
обещан только там.

### 4. Опросить пользователя

Показать предложенную разбивку нумерованным списком. Для каждого тикета:

- **Заголовок**: короткое описательное имя.
- **Заблокирован**: какими тикетами (если есть).
- **Что доставляет**: сквозное поведение, которое этот тикет включает.

Спросить пользователя:

- Гранулярность подходит (слишком крупно / слишком мелко)?
- Блокирующие рёбра верны — зависит ли каждый тикет только от того, что
  реально его гейтит?
- Что-то стоит объединить или разбить дальше?

Повторять, пока пользователь не одобрит разбивку.

### 5. Опубликовать тикеты в трекер

**Трекер выбирается переменной окружения `TICKETS_TRACKER`** (`local` по
умолчанию или `github`). `publish.sh` читает `.env` сам (грузит его в
свой процесс) и берёт `TICKETS_TRACKER` оттуда, если вызван без явного
режима — агенту не нужно и нельзя читать `.env` напрямую инструментом Read
(это заблокировано `permissions.deny` независимо от того, секрет там или
нет): проверить, что переменная вообще задана, можно через
`.claude/skills/env-check/env-check.sh TICKETS_TRACKER`. Сами тикеты
одинаковы в любом случае, меняется только форма блокирующих рёбер и место
публикации.

Сначала записать по одному markdown-файлу на тикет в рабочий каталог (см.
шаблон ниже), в порядке зависимостей (блокеры раньше блокируемых), затем
вызвать:

```bash
# без явного режима publish.sh сам берёт TICKETS_TRACKER из .env
.claude/skills/to-tickets/publish.sh --slug <feature-slug> --dir <каталог с тикетами>

# local явно — файлы остаются локально в .scratch/<feature-slug>/issues/
.claude/skills/to-tickets/publish.sh local --slug <feature-slug> --dir <каталог с тикетами>

# github — внешняя запись: сначала --dry-run и показать план,
# согласие пользователя на разбивку и точный текст — обязательно ДО
# вызова без --dry-run
.claude/skills/to-tickets/publish.sh github  --repo <owner/repo>    --dir <каталог> --dry-run
.claude/skills/to-tickets/publish.sh github  --repo <owner/repo>    --dir <каталог>
```

Без `--dry-run` `publish.sh` создаёт issue реально — это внешняя запись, и по
правилам движка (см. `AGENTS.md`) она делается только после явного согласия
пользователя на разбивку и точный текст каждого тикета. Скрипт сам честно
отказывает, если `GITHUB_TOKEN` отсутствует. Токен из окружения процесса
имеет приоритет над корневым `.env`, включая явно пустое значение; выбранный
токен используется общей библиотекой GitHub без раскрытия значения.

Работать **фронтиром**: любой тикет, у которого все блокеры уже готовы. Для
чисто линейной цепочки это сверху вниз.

Не закрывать и не менять родительский issue.

вставить его и коротко отметить, что он из прототипа. Оставлять только
насыщенную решениями часть, не рабочее демо целиком.
