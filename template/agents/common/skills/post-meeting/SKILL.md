# Post-Meeting

Из транскрипта звонка получить две вещи: заметку, которая через месяц
объяснит, о чём договорились, и обновлённое состояние команды (решения,
приоритеты); и — только если нужно — черновик сообщения, который владельцам
темы понятен без прослушивания записи.

Перед чтением/записью командных материалов разрешите `<knowledge-repo>` и
`<knowledge-root>` через skill **`knowledge`**, затем командный knowledge-skill.
Все `knowledge/...` пути ниже обозначают категории внутри этого resolved root,
а не каталог в workspace или фиксированный корень checkout.
Заметка идёт в `<knowledge-root>/meetings/` выбранного task-worktree. Отсутствующий checkout не создаёт локальный fallback.

## Триггер

- `/post-meeting` без текста → берём последнюю запись из `TRANSCRIPTS_DIR`
  (см. «Извлечение транскрипта» ниже).
- `/post-meeting` с текстом, вставленный транскрипт, «обработай последний
  звонок», «последний транскрипт», «пост-мит готов».

## Источник транскрипта

Два варианта входа:

1. **Вставленный текст** — пользователь вставил транскрипт или уже
   структурированные заметки. Использовать как есть.
2. **Последняя запись из `TRANSCRIPTS_DIR`** — папка с записями в формате
   Superwhisper и совместимых инструментов: `TRANSCRIPTS_DIR/<id>/meta.json`
   - `output.wav`. Без `TRANSCRIPTS_DIR` в `.env`
   (`.claude/skills/env-check/env-check.sh TRANSCRIPTS_DIR`) этот путь
   недоступен — сказать об этом и предложить вставить текст вручную, не
   гадать путь.

### meta.json — ключевые поля

| Поле | Тип | Описание |
|------|-----|----------|
| `datetime` | string | ISO-таймстамп начала записи |
| `duration` | int | Длительность в **миллисекундах** |
| `result` / `rawResult` | string | Сырой слой транскрипции, без разбивки по спикерам |
| `llmResult` | string | Постобработка LLM — разбивка по спикерам, пунктуация; есть не всегда |
| `segments` | array | `[{text, start, end}]` — таймкоды по сегментам (пословные у многих инструментов) |
| `languageSelected` / `languageModelName` | string | Выбранный язык и модель постобработки |

### Отбор нужной записи

- Записи короче ~10 минут обычно не встречи (диктовки, голосовой ввод) —
  не предлагать их автоматически, но не терять: если пользователь просит
  «последний звонок», а самая свежая длинная запись лежит не первой в
  списке, сортировка по времени не должна её прятать — листинг проходит по
  всем папкам, не по первым N.
- Показать превью (дата, длительность, первые ~200 символов) и дать
  пользователю подтвердить, если совпадений больше одного.

### Выбор слоя текста (`result` vs `llmResult`)

Общее правило, не привязанное к конкретной модели: `llmResult` даёт
разбивку по спикерам и обычно предпочтительнее, **но** его размер и хвост
нужно сверить с `result`, прежде чем доверять ему целиком —
постобработка изредка обрывает текст на середине длинной записи, а иногда
искажает таймкоды, не обрезая сам текст. Признаки:

- **Правдоподобно обрезан**: `len(result)` заметно больше `len(llmResult)`,
  и оба слоя не заканчиваются одной и той же фразой. В этом случае для
  части записи после обрыва брать `result` (без атрибуции по спикерам, но
  полный), и пометить в сохранённом транскрипте, что вторая часть — сырой
  слой.
- **Похоже на обрыв, но не обрыв**: `len(result) ≈ len(llmResult)`, оба
  заканчиваются одной фразой — тогда просто врут таймкоды внутри
  `llmResult`, содержание полное. Проверить по `segments` (настоящие
  таймкоды): темы конца записи должны находиться и в `llmResult`, и в
  `segments`.
- Не полагаться на встроенный в текст заголовок с длительностью, если он
  есть, — сверять с полем `duration` и с фактическим покрытием по
  `segments`.

### Проверка на петли (repetition loops)

Некоторые транскриберы зацикливаются на одной фразе и молча теряют
десятки секунд речи под видом связного текста. Группировка пословных
`segments` по минутам **не ловит** это (см. docstring скрипта) — использовать:

```bash
python3 .claude/skills/post-meeting/scripts/transcript-loop-check.py <путь-к-meta.json-или-id> --rms
```

Код возврата 1 значит: найдено окно петли, где RMS показывает речь, а не
тишину — эту часть транскрипт потерял. Прогонять на каждой записи, не
только когда что-то насторожило.

### Полнота: длина текста должна соответствовать длительности

Дешёвая проверка на каждую запись: `len(text) / (duration_ms/60000)` —
плотность символов в минуту. Резкое падение против остальной записи —
сигнал усечения или потери речи, разбираться перед тем, как писать заметку
по половине звонка.

## Алгоритм

### Шаг 1 — Структурировать транскрипт

Извлечь:

- **Участники** — кто был на встрече.
- **Ключевые решения** — что решили, с обоснованием.
- **Задачи** — кто что делает и к какому сроку.
- **Открытые вопросы** — что осталось нерешённым.
- **Контекст** — о чём вообще была встреча.

Если участник не идентифицирован по голосу — так и написать, не
додумывать по контексту без явного основания.

### Шаг 2 — Сохранить артефакты

1. **Заметка встречи**: `knowledge/meetings/YYYY-MM-DD-короткий-слаг.md` —
   контекст, решения, задачи, открытые вопросы.
2. **Решения**: если решение долговременное — отдельный файл в
   `knowledge/decisions/` (дата, причина, статус «действует»), не только
   строка в заметке встречи.
3. **Сырой транскрипт**: сохранить рядом (например
   `knowledge/meetings/transcripts/YYYY-MM-DD-слаг.txt`), не переписывать —
   это запись того, что было сказано.

### Шаг 3 — Черновик сообщения (если нужен)

Если из встречи должно родиться сообщение куда-либо (канал, чат,
рассылка) — **подготовить черновик и показать его пользователю**.
Отправка — отдельный, последний шаг, и только с явным согласием на точный
текст и точное место. Никогда не отправлять напрямую из этого шага.

### Шаг 4 — Отчитаться

Перечислить: какие файлы созданы/обновлены (с путями), черновик сообщения
целиком (если есть), открытые вопросы или неоднозначности из транскрипта.

## После отправки — сверка с тем, что реально ушло

Если пользователь позже прислал финальный текст (то, что он на самом деле
отправил, поправив черновик) — это ground truth, и он может расходиться с
тем, что уже записано в `knowledge/meetings/` и `knowledge/decisions/`.

Разошедшееся делится на два вида, и путать их нельзя:

1. **Противоречие/изменение факта** — другой владелец, другая цифра, другой
   срок, перевёрнутое решение. Это чинить: обновить артефакты, повторным
   поиском убедиться, что старой формулировки не осталось нигде.
2. **Сокращение ради краткости** — деталь убрана из сообщения, но остаётся
   верной. Это **не трогать**: внутренняя заметка сохраняет полный
   контекст, канальный пост — сокращённый по формату, оба правы для своей
   аудитории.

Главное правило различения: «убрал» ≠ «исправил». Чинить только
противоречия.

## Что не переносится из этого скилла

- Автоматическое удаление аудио или любых файлов после обработки — не
  делается никогда без явного запроса пользователя на конкретное
  действие. Хранение и очистку записей решает сам пользователь.
- Прямая отправка сообщения без предварительного показа черновика.

## Verification

1. **Транскрипт целый** — плотность текста (символы/минуту) не проваливается
   резко относительно самой записи; при расхождении `result` vs `llmResult`
   выбран более полный слой (см. выше), а не автоматически LLM-слой.
2. **Проверка на петли прогнана** (`transcript-loop-check.py --rms`) — код 0
   или явно объяснённые окна, которые оказались тишиной.
3. **Решение — это решение**, с владельцем, а не идея или обсуждение.
4. **Черновик показан, не отправлен** — отправка ждёт явного согласия.
5. **После сверки с финальным текстом**: повторный поиск по артефактам не
   находит старой (опровергнутой) формулировки нигде.

**Adversarial:** запись ещё идёт (`duration=0` — не значит «пустая», может
значить «пишется прямо сейчас»); два звонка в одной папке записей; участник
не идентифицирован по голосу — писать «не идентифицирован», а не гадать по
теме вопроса.
