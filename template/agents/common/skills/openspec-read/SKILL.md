# Чтение спек OpenSpec

**`openspec/specs/` — что система делает сегодня. `openspec/changes/` — что
кто-то предложил, и что может не поехать вообще.** Спутать их — единственная
ошибка чтения, которая ничего не ломает сразу: код, написанный по неодобренной
дельте, компилируется, проходит тесты и противоречит продукту.

## Когда

- Правите код, у которого есть спека — ветка задачи, находка ревью, фикс PR.
- Отвечаете на вопрос про требуемое поведение («так и задумано?», «что должно
  вернуться при X?»).
- Собираетесь предложить change: сначала надо знать, нет ли уже требования про
  это в существующей capability.
- Ревьюите код против требования.

## Где читать

Каталог со спеками — это репозиторий из поля `always` в `repos.json`
воркспейса, а место **внутри** этого чекаута — его поле `specRoot`. Требуется
`openspec` CLI (`command -v openspec`), иначе — честный отказ с подсказкой
установки, а не попытка читать файлы руками вместо CLI.

| Ситуация | Чекаут |
| --- | --- |
| открыта задача | `worktrees/<task>/<spec-repo>/<specRoot>` |
| вопрос без задачи | `packages/<spec-repo>/<specRoot>`, сначала обновите чекаут |
| в руках только ветка или PR | откройте её чекаутом задачи, затем `spec-trace/spec-ref.sh --worktree . --markdown` |

`<spec-repo>` — имя репозитория из `always`; `<specRoot>` — его поле
`specRoot` (может быть пустым, тогда `openspec/` лежит в корне чекаута).
Читайте оба поля из `repos.json`, не угадывайте и не жёстко прописывайте
конкретное имя репозитория — у разных команд спека может лежать в другом
репозитории или в корне.

**CLI ищет ближайший `openspec/` выше cwd**, и это ровно то, что делает ошибку
незаметной: корневой `openspec/` в чекауте spec-repo может не существовать
(например, когда там же лежит и слой конфигурации агента) — тогда команда из
корня чекаута падает с понятной, но бесполезной ошибкой, а из корня воркспейса
падает так же тихо, просто найдя не тот `openspec/`, если он там случайно
есть. Поэтому `cd` делается до каталога `<specRoot>`, а не до корня чекаута:
адресация спек начинается там и нигде больше.

## Что чем достаётся

```bash
cd worktrees/<task>/<spec-repo>/<specRoot>

openspec list --specs                                   # какие capability есть
openspec show <capability> --type spec --json --no-scenarios # требования без сценариев
openspec show <capability> --type spec --json -r 3      # одно требование по номеру
openspec list                                           # changes в полёте
openspec show <change> --json --deltas-only             # только дельты change
openspec status --change <change>                       # какие артефакты готовы
openspec validate --all
```

`show --json` отдаёт разобранную структуру — `requirements[].text`,
`requirements[].scenarios[]`, `requirementCount` — и это дешевле и точнее, чем
читать markdown глазами: нумерация для `-r` берётся оттуда же. Остальные флаги —
в `--help`, не переписывайте их сюда.

Grep уместен ровно для одного: найти capability по термину домена, когда
неизвестно, в какой она лежит — `grep -rl "<термин>" openspec/specs/`.

## Формат главной спеки

`openspec/specs/<capability>/spec.md`, и это **capability, а не репозиторий**:
одна возможность продукта может жить в нескольких репозиториях сразу.

```markdown
## Purpose            ← зачем capability существует
## Requirements
### Requirement: <название требования>
Система SHALL ...                    ← RFC 2119: SHALL / MUST / SHOULD / SHALL NOT
#### Scenario: <название сценария>
- **WHEN** ...
- **THEN** ...
- **AND** ...
```

**Требование — это `### Requirement:`, а не абзац рядом с ним.** Сценарии под ним
проверяемы построчно и есть готовый чек-лист для тестов: тест, который прошёл бы
и без фичи, не покрывает сценарий.

Главная спека может дополнительно нести свёрнутые из архивных changes `##
Proposal` и `## Design` — `openspec validate` их пропускает. **Это не
артефакты change в полёте**, не ищите под ними change с таким же именем и не
судите код по ним: судят по `## Requirements`.

## Дельты в changes/

```text
openspec/changes/<change>/
  proposal.md          зачем и что меняем + затронутые репозитории, вне рамок
  design.md            технические решения (опционально)
  tasks.md             чек-лист задач
  specs/<capability>/spec.md   дельта — только то, что меняется
  implementation.md    трасса: репозитории, ветки, PR, коммиты (пишет spec-trace)
  .openspec.yaml       schema + дата создания
```

Дельта состоит из операционных заголовков, которых в главной спеке не бывает:

- `## ADDED Requirements` — новые требования целиком.
- `## MODIFIED Requirements` — правка существующего требования.
- `## REMOVED Requirements` — только заголовок `### Requirement: <имя>`, без тела.
- `## RENAMED Requirements` — строки `- FROM: \`### Requirement: Старое\`` /
  `- TO: \`### Requirement: Новое\``.
- `## Purpose` в дельте появляется **только** когда change заводит новую
  capability, и тогда он засеивает будущую главную спеку.

### `MODIFIED` — не полное состояние требования

Слияние дельты в главную спеку **сохраняет сценарии, которых в дельте нет**.
Значит по блоку `MODIFIED` нельзя судить, сколько у требования сценариев и какие:
два сценария в дельте не означают, что их всего два. Полный набор — только в
`openspec/specs/<capability>/spec.md`, и читать надо оба файла рядом.

Обратное тоже верно: сценарий, который в `MODIFIED` переписан, в главной спеке
ещё старый. Требование в полёте — это главная спека **плюс** дельта, а не одна
из них.

## Правда — это композиция

1. `openspec/specs/` — база.
2. Плюс дельты тех changes, чей код **влит**, но которые ещё не заархивированы:
   `openspec archive` фолдит дельту в главную спеку только после мержа PR, так
   что между мержем и архивацией правда разъехана по двум файлам.
3. `openspec/changes/archive/YYYY-MM-DD-<name>/` — история; читают, чтобы понять
   *почему* требование такое, а не чтобы узнать текущее поведение.

Что из change реально доехало до кода, говорит его `implementation.md` — ветки,
PR и коммиты по каждому репозиторию (см. скилл `spec-trace`). Пустая колонка PR
значит, что подтверждённый URL отсутствовал в локальном coordination record, а
не доказывает отсутствие PR в GitHub.

### Дельты складываются друг на друга

Capability может **вообще не существовать** в `openspec/specs/`: её завёл change,
который ещё не заархивирован, а следующие changes уже правят его дельту. Тогда
одно требование живёт в нескольких файлах — `## ADDED` в первом change,
`## MODIFIED` в следующих, — и каждый следующий расширяет предыдущий, а не
главную спеку.

Поэтому прежде чем отвечать про требование:

```bash
ls openspec/specs/<capability>/ 2>/dev/null || echo "в specs/ этой capability нет"
grep -rln "### Requirement: <имя>" openspec/specs openspec/changes/*/specs
```

Порядок цепочки — по `created` в `.openspec.yaml` каждого change, а также по тому,
что дельта говорит про себя сама: `MODIFIED` часто открывается цитатой-примечанием
о том, какой change ввёл требование и что здесь расширяется.

## Границы

Скилл про чтение. Писать спеки — апстримные скиллы самого спек-репо
(`openspec-propose`, `openspec-update-change`, `openspec-sync-specs`,
`openspec-archive-change`), и они читаются из чекаута спек, а не из корня
воркспейса: читайте нужный `SKILL.md` из чекаута и следуйте ему. Ссылки между
спекой и кодом — скилл `spec-trace`.

## Отмазки

| Отмазка | Реальность |
| --- | --- |
| «дельта в `changes/` свежее главной спеки — прочитаю её» | Она может быть не одобрена, а её код не влит. Свежесть здесь не признак правды. |
| «в `MODIFIED`-блоке два сценария — значит у требования их два» | Слияние сохраняет неупомянутые сценарии. Полный набор только в `specs/`. |
| «спека длинная, прочитаю `proposal.md` — там суть» | Proposal говорит «зачем меняем». Код судится по `### Requirement:`, а не по мотивации. |
| «`## Design` в главной спеке — значит это change» | Это свёрнутый архив. Change живёт в `changes/`. |
| «grep быстрее, чем разбираться с CLI» | Grep находит файл. Требование с его сценариями и нумерацией отдаёт `show --json` — и не врёт про границы блока. |
| «уже смотрел эту спеку» | Чекаут мог отстать. Обновление стоит секунду, ответ по устаревшей спеке — уверенный и неверный. |

## Красные флаги

- Пишете код, назвав требование по `proposal.md` или по названию change.
- Судите поведение по дельте, не открыв главную спеку рядом.
- Ищете capability по имени репозитория — их так не зовут.
- Запускаете `openspec` из корня воркспейса или из корня чекаута без `cd` в `specRoot`.
- Правите ветку, не спросив `spec-ref.sh`, какую спеку она реализует.
