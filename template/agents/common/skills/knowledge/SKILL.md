# Knowledge routing

Этот skill отвечает на три вопроса: **кто фиксирует знание, когда оно уже
достаточно устойчиво и куда именно его класть**. Он не заменяет предметный skill
вроде `post-meeting`, `notion-snapshot` или `spec`; он сначала выбирает
канонический checkout, а затем передаёт ему запись.

## Сначала найдите канонический репозиторий

Источник конфигурации — корневой `repos.json`, а не имя конкретной команды.
Для каждого репозитория из `always` возьмите `knowledgeRoot` (без поля —
`knowledge`; явное `"."` означает корень репозитория) и проверьте каталог `<knowledge-root>/` в актуальном checkout
задачи или в `packages/`. Должен найтись **ровно один**
`<knowledge-repo>`:

- один кандидат — это канонический knowledge-репозиторий;
- ни одного — ничего не создавайте по догадке, сообщите, что в `always` не
  настроен репозиторий с каталогом знаний;
- несколько — перечислите их и запросите явный выбор/исправление манифеста;
  порядок в `always` не является приоритетом.

Перед выводом «ни одного» убедитесь через skill `clone`, что checkout'ы всех
`always`-кандидатов действительно наполнены и обновлены. Отсутствующий
`packages/<repo>` означает «не проверено», а не «там нет knowledge». Имя
кандидата берите только из ключей `repos.json`; итоговый real path должен
оставаться внутри выбранного checkout. `knowledgeRoot` — непустой относительный
POSIX-путь; `"."` выбирает сам checkout. Пустое значение не означает корень.
Абсолютный путь, `..`, обратный слеш и symlink, выходящий из checkout,
запрещены. Отсутствующий настроенный каталог — ошибка, а не повод писать в
старый `knowledge/`.

Проверку выполняет `.claude/skills/knowledge/resolve.py <workspace>`; для записи
передайте `--task-dir <workspace>/worktrees/<task>`. JSON называет `repo`, `root`,
`checkout` и `url`. `--allow-missing` служит только manifest-only проверке линтера,
никогда записи.

`packages/<knowledge-repo>/<knowledge-root>/` — только чтение дефолтной ветки.
**Любая авторская запись** идёт в
`worktrees/<task>/<knowledge-repo>/<knowledge-root>/`. Никогда не правьте `packages/`,
корень воркспейса или сгенерированные `.claude/`/`.agents/` вместо worktree.

Если задача уже открыта, используйте её `<task>` и убедитесь, что checkout
knowledge-repo в ней есть. Для knowledge-only задачи создайте worktree явно:
`.claude/skills/wt/wt new <task> --repo <knowledge-repo> --pull`. Голый
`wt new <task>` из корня не задаёт исходный репозиторий, даже если тот находится
в `always`. Одно изменение во всех репозиториях использует одно имя задачи,
одну ветку задачи и связанные PR.

При `knowledgeRoot: "."` категории лежат прямо в репозитории: `facts/`,
`decisions/`, `meetings/`, `projects/`, `references/`, `changelog/`.
Например, заметка встречи записывается в
`worktrees/<task>/<knowledge-repo>/meetings/YYYY-MM-DD-<slug>.md`.
Не добавляйте к этому пути `knowledge/` и не создавайте его заново.
Отсутствующее поле сохраняет прежний путь `<knowledge-repo>/knowledge/`;
явное `"."` и отсутствие поля имеют разный смысл. `specRoot` независим:
при `specRoot: ""` требования остаются в `<knowledge-repo>/openspec/`.

## Кто, когда и куда пишет

Подкаталоги ниже — стандартный контракт движка. Командный `AGENTS.md` может
сузить критерии и формат, но не может превращать `packages/` в место записи.

| Знание | Кто фиксирует | Когда фиксировать | Куда внутри `<knowledge-root>/` |
| --- | --- | --- | --- |
| Проверенный устойчивый факт | оркестратор после проверки источника и подтверждения владельцем знания | факт пригодится будущей задаче и подтверждён источником | `facts/` |
| Долговременное решение | оркестратор после явного решения владельца | выбран один вариант, важны причина, статус и последствия | `decisions/` |
| Контекст команды и словарь | команда или агент после проверки | объяснение стабильно и нужно для понимания других материалов | `context/` |
| Инцидент | участник расследования | известны impact, timeline, root cause или честно отмечены пробелы | `incidents/` |
| Встреча | `post-meeting` или назначенный участник | есть transcript/заметки и отделены решения от action items | `meetings/` |
| Долгий проект/инициатива | владелец проекта | материал переживает одну задачу или PR | `projects/` |
| Внешний первоисточник/слепок | специализированный sync/snapshot skill | источник нужен офлайн и понятны происхождение и дата | `references/`; см. исключение для зеркал ниже |
| Стратегия | владелец направления | зафиксированы цель, горизонт и допущения | `strategy/` |
| Пользовательски заметное изменение командного агентского слоя | автор изменения | перед закрытием PR с новым/изменённым поведением `agents/` | `changelog/YYYY-MM-DD-<slug>.md`; если настроены хранилище и skill **`changelog`**, он определяет необходимость и ссылки; иначе запись не требуется |
| Требования к поведению продукта | analyst/architect через специализированный spec workflow | поведение должно быть проверяемым и согласованным до кода | `<specRoot>/openspec/`; используйте skill **`spec`** |

Сначала ищите существующий файл и обновляйте его, если это та же сущность.
Новый файл не должен дублировать уже принятое решение, факт или проект. Имена,
индексы решений и локальный шаблон берите из соседних файлов, не из этой
таблицы.

## Правила качества

1. Отделяйте доказанный факт от вывода и предположения; прикладывайте ссылку на
   код, PR, тикет, источник или дату наблюдения.
2. Самоинициированную запись факта не выдавайте за слова пользователя. Если
   точная формулировка влияет на смысл, сначала подтвердите её.
3. У встречи отдельно храните решения, открытые вопросы и action items. Секреты,
   токены и чувствительный сырой transcript в Git не переносите.
4. Зеркало внешнего источника не становится новой истиной: укажите origin,
   время слепка и специализированный skill, которым оно обновляется.
5. Для OpenSpec-артефактов не выбирайте путь по этой таблице вручную — skill
   `spec` вычисляет `<specRoot>/openspec` из манифеста.
6. Analyst и architect могут писать только свои OpenSpec-артефакты. Обычные
   knowledge-файлы и Git lifecycle остаются у оркестратора.

## Узкое исключение: автоматизированные зеркала

Полный machine-generated snapshot внешней системы может использовать lifecycle,
который явно описан его source-specific skill: временный checkout, фиксированную
ветку и переиспользуемый Draft PR. Это допустимо только когда всё ниже истинно:

- source-specific skill разрешил `notionSnapshotRepo` из `repos.json`, если поле
  настроено; `null` запрещает публикацию и любые env overrides; только отсутствие
  поля допускает прежнее discovery канонического `<knowledge-repo>`;
- целевой каталог остаётся внутри `<knowledge-root>/references/` выбранного snapshot
  checkout (`references/` при `knowledgeRoot: "."`, `knowledge/references/` без поля); настройка зеркала не меняет маршрут авторских знаний;
- skill сохраняет provenance и полностью владеет повторным sync/delete;
- ветка и PR не используются для авторских facts, decisions, meetings или specs.

Например, `notion-snapshot` — такое зеркало. Его fixed-branch flow является
исключением для воспроизводимой машинной копии, а не альтернативным способом
писать knowledge руками. Если source-specific skill не объявляет такой контракт,
действует обычный task-worktree flow.

## Закрытие

Для обычной записи проверьте diff только в `worktrees/<task>/`, запустите проверки репозитория,
закоммитьте и откройте Draft PR через `commit-and-mr`. Если знание сопровождает
код в других репозиториях, свяжите PR одной задачи; не создавайте отдельный
неотслеживаемый checkout или ветку только ради markdown-файла.

## Красные флаги

- запись напрямую в `packages/<knowledge-repo>/<knowledge-root>/`;
- жёстко прописанное имя team/soul-репозитория вместо `repos.json`;
- первый из нескольких кандидатов выбран молча;
- новая заметка дублирует существующий факт/решение;
- спека создана в `knowledge/specs`, но вне `<specRoot>/openspec`;
- авторская заметка отправлена в fixed snapshot branch;
- знание осталось только в чате, хотя оно определяет будущую работу.
