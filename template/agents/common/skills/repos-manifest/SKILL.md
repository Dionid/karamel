# Манифест репозиториев

`repos.json` описывает состав workspace и маршрутизацию; каталог `packages/`
не заменяет манифест и не является местом для авторских правок.

## Сначала определите операцию

- Для вопроса о полях читайте [schema.md](schema.md): там полный справочник,
  defaults, ограничения и потребители. Сверяйте спорное поведение с указанным
  кодом: единой JSON Schema и общего строгого валидатора сейчас нет.
- Для создания или изменения манифеста работайте в task-worktree репозитория
  workspace через [wt](../wt/SKILL.md) и [coordination](../coordination/SKILL.md).
  Корневой checkout и `packages/` вручную не правьте.
- Для наполнения `packages/` используйте [clone](../clone/SKILL.md), а для
  спецификаций и знаний — [spec](../spec/SKILL.md) и
  [knowledge](../knowledge/SKILL.md). Этот skill не создаёт контент этих repos.

## Создать или изменить

1. Прочитайте текущие `repos.json`, `PACKAGES.md` и справочник. Уточните только
   неизвестные URL, base branch или назначение repo. Не выводите имя каталога
   из URL: ключ `repos` — самостоятельное имя, используемое командами.
2. Для нового workspace создайте объект с `repos`. У каждой записи задайте
   credential-free `url`; явно задайте согласованную `branch`, чтобы remote
   default не определял базу незаметно. Минимальный пример — в справочнике.
3. Добавьте лишь нужные настройки. `always` — не каталог всех репозиториев;
   он расширяет каждую задачу. `exclude` — не удаление записи и не запрет
   явного клонирования. Не добавляйте dependency-флаги вместо `deps`.
4. При удалении записи проверьте ссылки из `always`, `notionSnapshotRepo` и
   `PACKAGES.md`. Удаление записи не удаляет checkout, worktrees или данные;
   их cleanup выполняется отдельной процедурой `wt`.
5. Hooks — исполняемый Bash, а не описание: проверьте cwd, повторный запуск,
   отсутствие секретов в тексте/выводе и стоимость команды. Для установки в
   Node worktree применяйте `npm install`, сохраняя copy-on-write зависимости.
6. Проверьте JSON и diff. Запустите из изменённого checkout `./ops check
   --scratch` и workspace lint по [lint](../lint/SKILL.md). Это не полная
   проверка всех полей: дополнительно проверьте имена ссылок, пути и отсутствие
   неоднозначной knowledge/spec маршрутизации по справочнику.
7. Закройте изменение штатным review и [commit-and-mr](../commit-and-mr/SKILL.md).
   После доставки в корневой checkout наполнение выполняет `clone`; `./ops sync`
   подключает repo-skills только из `packages/`. В task-worktree sync не нужен.

## Обновить из существующих checkout'ов

`.claude/skills/wt/wt manifest` пишет `repos.json` найденного workspace-root,
поэтому сначала проверьте, **какой файл будет изменён**. Запускайте только в
контексте разрешённого task-worktree с его `packages/`, а не ради быстрого
обновления корневого checkout. Обычный task-worktree такого каталога не имеет:
в этом случае сверяйте credential-free origin/base нужных checkout’ов
read-only и редактируйте соответствующие записи в task-worktree вручную.
Не создавайте и не клонируйте дополнительный набор repos только ради refresh.

Команда сканирует git-repos в `packages/`, пропускает `exclude` и записи без
origin, обновляет URL и добавляет новые записи. Существующая непустая `branch`
сохраняется даже при расхождении с origin/HEAD (будет предупреждение).
Остальные поля и записи без checkout сохраняются; это не pruning и не
валидация всей схемы. Смену base branch вносите явно после проверки назначения.

## Что сообщить

Перечислите изменённые записи и поведение (`always`, hooks, подключение скиллов,
маршрутизация), проверки и оставшиеся missing checkout'ы. Отдельно укажите,
нужно ли после merge наполнить `packages/` и выполнить sync в корне.
