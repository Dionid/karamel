# Spec routing

Этот skill задаёт общий адрес и границу ответственности для продуктовых
спецификаций. После маршрутизации используйте подходящий процедурный skill:
`spec-loop` для согласованного цикла до кода или точечный `openspec-*` для уже
понятной операции.

## Когда нужна спека

OpenSpec нужен, если изменение задаёт или меняет **наблюдаемое поведение
продукта**: контракт API, пользовательский сценарий, бизнес-правило, состояние,
совместимость или проверяемый отказ. Сценарий должен позволять отличить
реализацию требования от кода, который прошёл бы тест и без изменения.

Не заводите продуктовую capability только ради внутреннего рефакторинга,
инфраструктурной настройки, агентского процесса или организационной заметки.
Такие долговременные материалы маршрутизирует skill **`knowledge`**. Если
техническая работа всё же меняет внешний контракт, спека описывает именно этот
контракт, а не список файлов и команд.

## Как найти spec-repo и spec-root

Читайте корневой `repos.json`. Кандидат в spec-store — **любая** запись с полем
`specRoot` (пустое значение означает корень checkout), а не только репозиторий
из `always`: у продукта может быть собственный store в его же репозитории, и в
каждый worktree такой репозиторий не попадает. Записи `always` без `specRoot`
остаются кандидатами по-старому, от корня checkout. Проверьте каталог
`<repo>/<specRoot>/openspec` у каждого кандидата:

- один — его имя становится `<spec-repo>`, нормализованный `specRoot` —
  `<spec-root>`;
- ни одного — остановитесь: workspace не настроил OpenSpec-хранилище;
- несколько — store выбирает **субъект изменения**, а не порядок манифеста:
  спека продукта живёт в store этого продукта. Кандидат для субъекта должен
  быть ровно один; если субъект неоднозначен — изменение задевает продукты
  разных store — остановитесь и спросите пользователя, в какой store писать.
  Не выбирайте первый кандидат молча и не пишите в оба.

Перед выводом «ни одного» наполните/обновите `always`-checkout'ы через `clone`:
missing checkout — это неизвестность, не отрицательный match. `specRoot` —
**родитель** каталога `openspec`, а не сам `openspec`; значение с последним
сегментом `openspec` диагностируйте отдельно как вероятный double-path.

До использования пути отвергните абсолютный `specRoot`, сегменты `..` и любой
symlink/realpath, который выводит `<specRoot>/openspec` за пределы checkout.
После `realpath` и checkout, и marker должны существовать, а marker должен
начинаться с real path checkout плюс разделитель. Некорректный путь — ошибка
манифеста, его нельзя «нормализовать» до другого каталога.

Если доступен `spec-trace/spec-checkout-lib.sh`, используйте его функции
`spec_prefix_for` и `find_spec_checkout` для той же manifest-based адресации.
При нескольких кандидатах `find_spec_checkout` сам отказывает кодом 2 и
перечисляет их; субъект называют переменной `SPEC_SUBJECT_REPO=<repo>` — но
только когда пользователь его уже подтвердил, иначе переменная превращает
отказ в ту самую догадку, ради предотвращения которой он сделан.

Канонический путь записи всегда такой:

```text
worktrees/<task>/<spec-repo>/<spec-root>/openspec/
```

При пустом `<spec-root>` двойной разделитель не добавляется: получается
`worktrees/<task>/<spec-repo>/openspec/`. `packages/<spec-repo>/...` допустим
только для read-only вопроса без открытой задачи. Любое создание, обновление,
sync или archive выполняется в worktree задачи.

Если OpenSpec CLI сообщает `planningHome.root` или registered store вне
checkout, не пишите туда в командном workflow. Сначала store должен стать
репозиторием из manifest и checkout'ом этого же worktree; иначе у изменения не
будет обычных diff, review и PR.

## Кто пишет что

| Артефакт | Ответственный | Место |
| --- | --- | --- |
| `proposal.md`, delta specs | analyst | `openspec/changes/<change>/` |
| `design.md`, `tasks.md` | architect | тот же change |
| approval ledger и порядок стадий | orchestrator через `spec-loop` | ledger задачи, не подмена артефактов |
| main specs после реализации | `openspec-sync-specs` / `openspec-archive-change` | `openspec/specs/<capability>/` |
| код | builder после одобрения | продуктовые checkout той же задачи, не spec-repo вместо них |

Роли не редактируют артефакты друг друга: они делают cross-read и возвращают
findings автору. Явное одобрение пользователя относится к показанной версии;
существенная правка снова открывает весь пакет на одобрение.

## Последовательность

1. Создайте/используйте `worktrees/<task>/` через `wt`; spec-repo должен
   оказаться в том же worktree, что и продуктовый код. Store не из `always`
   подтягивается явно: `wt new <task> --repo <spec-repo>`.
2. Перейдите в `worktrees/<task>/<spec-repo>/<spec-root>`. Все команды
   `openspec` запускайте отсюда, чтобы CLI видел правильный `openspec/`.
3. Прочитайте текущие specs и активные changes через `openspec-read`.
4. Для неоднозначного изменения проведите `spec-loop`; для точечной операции —
   соответствующий `openspec-propose`, `openspec-update-change`,
   `openspec-sync-specs` или `openspec-archive-change`.
5. После каждой записи выполните `openspec validate`; перед передачей в build —
   `openspec status --change <change>` и финальную валидацию.
6. Коммитьте spec-repo в ветке той же задачи. `commit-and-mr` и `spec-trace`
   связывают спецификацию, реализации и PR; отдельная скрытая ветка для спеки
   не нужна.

## Красные флаги

- `openspec` запущен из корня workspace или checkout вместо `<spec-root>`;
- запись сделана в `packages/`;
- имя spec-repo или `knowledge/specs` зашито в skill/промпт без чтения
  `repos.json` и `specRoot`;
- store выбран по тому, что уже лежит в worktree, а не по субъекту изменения;
- proposal, design и tasks написаны разом до вопросов пользователю;
- внутреннее устройство выдано за продуктовое требование;
- code phase началась до одобрения артефактов;
- `openspec archive` выполнен до того, как реализация смёржена.
