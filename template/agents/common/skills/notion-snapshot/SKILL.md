# Слепок Notion в репозиторий

**Один прогон — полное состояние дерева, а не добавка к предыдущему.** Скрипт
обходит корни из `notion.json` в корне репозитория скиллом `notion`,
кладёт страницы в `<каталог>/<root>/` целевого репозитория и пушит фиксированную
ветку по HTTPS через gh. Нет открытого PR у ветки — `gh pr create` открывает
Draft PR; есть — push его обновляет. Страница, удалённая или переименованная в Notion, из
коммита исчезает — каталог корня перезаписывается целиком.

```bash
.claude/skills/notion-snapshot/run.sh                    # все корни
.claude/skills/notion-snapshot/run.sh --root team        # один корень
.claude/skills/notion-snapshot/run.sh --dry-run          # что изменилось бы
.claude/skills/notion-snapshot/run.sh --no-push --keep <dir>   # только дамп
```

`--depth N|max`, `--no-dbs`, `--no-links`, `--link-depth N`, `--max-pages N`,
`--allow-partial`, `--branch`,
`--title` — `--help` печатает все. Без `--depth` каждый корень читается на свою
`maxDepth` из манифеста, и это правильный дефолт: глубина — свойство корня, а
не прогона.

**Обход глубокий по умолчанию в обе стороны:** строки баз данных читаются, и
ссылки на Notion внутри текста страниц тоже — флага для этого не нужно.
Поэтому слепок корня, который много на что ссылается, стоит минуты или часы:
прежде чем поднимать `maxDepth` такому корню, прикиньте размер. Выключается
это на один прогон (`--no-dbs`,
`--no-links`) или на корень (`"dbs": false`, `"links": false` в `notion.json`).

Две границы обхода задаются отдельно от `maxDepth`, потому что дерево
кончается, а граф ссылок — нет: `--link-depth N` (по умолчанию 2) — сколько
переходов по ссылкам за пределы дерева делать, и `--max-pages N` (по умолчанию
2000) — бюджет страниц на корень. **Упёршийся в бюджет прогон не коммитится**:
страницы, до которых он не дошёл, в дереве-замене выглядят ровно как
удалённые в Notion.

## Куда именно едет слепок — конфигурация, не хардкод

Сначала прочитайте `repos.json.notionSnapshotRepo`: это отдельное назначение
машинного зеркала, которое может находиться вне `always`. Строка выбирает
репозиторий из манифеста; `null` явно отключает публикацию до проверки
credentials и обхода Notion, даже при `NOTION_SNAPSHOT_PROJECT` и
`NOTION_SNAPSHOT_ALLOW_FOREIGN_PROJECT=yes`. Задайте отдельный репозиторий
машинного зеркала; авторские знания и спеки в него не переносятся.
Чтение через `notion` и локальный дамп `--no-push` доступны независимо от публикации.

Если `notionSnapshotRepo` отсутствует, discovery выполняет `knowledge/resolve.py` по
единственному `always`-репозиторию, включая явный `knowledgeRoot` и legacy `knowledge/`.
Некорректное явное поле — отказ даже при `NOTION_SNAPSHOT_PROJECT`: оно не
переключается молча на канонический репозиторий или origin workspace.

`NOTION_SNAPSHOT_PROJECT`, если задан, сверяется с snapshot-назначением по
host/path. Несовпадение останавливает прогон до обхода; осознанный foreign
project требует `NOTION_SNAPSHOT_ALLOW_FOREIGN_PROJECT=yes`. Без явного поля
и без legacy-кандидата override может задать цель самостоятельно.
`NOTION_SNAPSHOT_DIR` по умолчанию — `<knowledgeRoot>/references` выбранного
snapshot-репозитория: `references/` при `knowledgeRoot: "."`,
`knowledge/references/` без поля. Переопределение разрешено только внутри этого
каталога; абсолютные пути, `..` и symlink за пределы checkout запрещены.
Для отдельного `notionSnapshotRepo` читается его собственный `knowledgeRoot`;
foreign override использует `knowledgeRoot` своей записи в манифесте,
а неизвестный манифесту репозиторий — legacy `knowledge/references/`.

Коммитер тоже часть права на запись: `NOTION_SNAPSHOT_GIT_EMAIL` проверяют push
rules целевого проекта. Задавайте разрешённый адрес явно до прогона:
встроенный placeholder `notion-snapshot@localhost` не является рабочей identity.
`run.sh` отказывает до обхода, если email пуст или остался placeholder;
допустимые домены определяет целевой проект, а не общий skill.

Этот skill — объявленное `knowledge` исключение для автоматизированного зеркала:
он использует временный checkout, фиксированную ветку и переиспользуемый Draft
PR вместо task worktree. Исключение не распространяется на авторские заметки,
факты, решения, встречи или спеки.

Целевой репозиторий, каталог и ветка — переменные `env`, не встроенные в код
значения:

```bash
NOTION_SNAPSHOT_PROJECT=   # "group/path" или полный URL; пусто — цель
                           # разрешается из repos.json, без fallback на origin
NOTION_SNAPSHOT_DIR=       # по умолчанию: <knowledgeRoot>/references
NOTION_SNAPSHOT_BRANCH=    # по умолчанию: notion/snapshot
NOTION_SNAPSHOT_GIT_EMAIL= # обязателен; адрес из push-rule целевого проекта
NOTION_SNAPSHOT_ALLOW_FOREIGN_PROJECT=  # yes — снять сверку, но не запрет null
```

`env.example` рядом с этим файлом перечисляет их с подсказками; `--branch`
переопределяет `NOTION_SNAPSHOT_BRANCH` на один вызов.

## Перед первым прогоном — право и согласие

- **Доступ к GitHub проверяет сам скрипт** через
  [`commit-and-mr/lib.sh`](../commit-and-mr/lib.sh), используя только
  `GITHUB_TOKEN` из окружения процесса или корневого `.env` (окружение
  приоритетнее, включая пустое значение). Базовая ветка берётся из
  `git ls-remote --symref` по HTTPS. Нет доступа — отказ до обхода.
  `--no-push --keep <dir>` позволяет сохранить дамп без git-доступа.
- **Прогон необратим наружу** — он пушит ветку; если у неё нет открытого PR,
  также открывает Draft PR через `gh pr create`. Поэтому согласие спрашивается
  текстом, как для любой записи в GitHub. `--dry-run` и `--no-push` не
  спрашиваются: они читают Notion, ничего не записывая.
- **Это минуты, а не секунды.** Два запроса на страницу при лимите ~3/с —
  контент и её `last_edited_time` для фронтматтера — корень команды это около
  четырёх минут. Скажите ожидаемое время до запуска, а не после.

## Что именно попадает в репозиторий

```text
<каталог>/README.md          корни из `notion.json`, дата снимка, «это копия»
<каталог>/<root>/INDEX.md    карта поддерева с отступами и ссылками
<каталог>/<root>/<путь>.md   страница; её дети — в каталоге <путь>/
<каталог>/<root>/_linked/    страницы, до которых дошли по ссылке, но которых
                             нет в дереве корня
```

Имена — из заголовков, транслитом в ASCII, а не по порядку обхода
(`--layout nested` у `notion.sh dump`). Это и есть причина, по которой слепок
годится для git: вставленная в Notion страница меняет свой файл и `INDEX.md`,
а не переименовывает сотню соседних. У каждого файла фронтматтер с `id`,
`url` и `edited` — по `id`/`url` страница находится в Notion и после
переименования, `edited` — её `last_edited_time` на момент прогона.

**Слепок — копия, а не источник.** Правка файла в репозитории в Notion не
уезжает и теряется на следующем прогоне; менять надо страницу по `url` из
фронтматтера. Обратное направление — скилл `notion-publish`.

Свежесть конкретного файла слепка проверяется без похода в git:
`notion.sh edited <id>` (id — из фронтматтера того же файла) против записанного
там же `edited` — разошлись, значит страницу поправили после этого прогона, и
её стоит перечитать (`notion.sh page <id>`) перед тем как на неё ссылаться.

## Ветка одна, доставка через gh

Фиксированная ветка (`NOTION_SNAPSHOT_BRANCH`, по умолчанию `notion/snapshot`)
продолжается, если она уже есть на origin; иначе создаётся от базовой ветки.
Пуш идёт по HTTPS с credential helper gh. После push скрипт ищет открытый PR
ветки через `gh pr list`: нашёлся — `MR_STATE=existing`, push его уже
обновил; нет — `gh pr create` открывает Draft PR (`MR_STATE=created`).
Если gh не смог ответить, второй PR не открывается наугад —
`MR_STATE=unknown`. Описание существующего PR скрипт не переписывает.

Нет `gh`, нет `GITHUB_TOKEN`, токен отклонён или сеть недоступна — отказ до
обхода Notion. Настройку credentials ведёт `github-login`; доставка использует
только HTTPS и тот же выбранный токен для git и GitHub API.

## Что докладывать

| `SNAPSHOT_STATE` | Что случилось |
| --- | --- |
| `committed` | коммит на ветке, плюс `COMMIT_SHA`, `CHANGED_FILES`, `DIFF` и `MR_STATE`/`MR_URL` |
| `unchanged` | Notion не двигался с прошлого прогона — результат, а не сбой; `MR_STATE` — `existing` с URL, `none` или `unknown` |
| `dry-run` | дифф посчитан, ничего не записано |
| `dump-only` | `--no-push`: дамп лежит в `DUMP_DIR`, репозиторий не тронут |

В ответе — ссылка на PR, если gh её вернул (`created` или `existing`);
иначе ветка и `MR_STATE`.
Также укажите число изменённых файлов и число страниц по корням.

**Корень, который не проходится за один раз, снимается за несколько.**
`--cache DIR` держит разметку каждой страницы рядом с её `last_edited_time`,
поэтому следующий прогон спрашивает только «изменилась ли», а тело тянет лишь
у изменившихся — вдвое меньше запросов. `--resume` к тому же кэшу не
спрашивает ничего: уже пройденное переигрывается почти мгновенно, и обход
идёт дальше, туда, куда в прошлый раз не дошёл. Замерено на 40 страницах:
80 с вхолодную, 41 с с `--cache`, 5.7 с с `--resume`.

Цена у `--resume` одна и названа честно: страницу, изменившуюся после
попадания в кэш, он не заметит. Поэтому последовательность такая — несколько
прогонов с `--resume`, пока дерево не закроется, и один без него, чтобы
подобрать изменения.

**Ссылка в недоступную страницу — не дыра в слепке.** Обход ходит по ссылкам,
а значит регулярно упирается в страницы, к которым интеграция не подключена.
Они попадают в `UNREACHABLE_LINKS` и в описание PR, но не в `SKIPPED_PAGES` и
не блокируют коммит: слепок не содержит их и не должен — эта страница никогда
не была частью этого дерева. Счётчик страниц в сводке поэтому не значит «всё,
на что ссылается корень, лежит здесь».

**Обход, который не прочитал часть дерева, скрипт не коммитит.** `PAGES=0`
означало бы удаление всего слепка, `SKIPPED_PAGES` — удаление именно той
части, которая не прочиталась, поэтому оба случая — отказ, а второй снимается
явным `--allow-partial`. `TRUNCATED_PAGES` (на странице остались блоки,
которые API не отдал, — обычно не расшаренные интеграции) не блокирует, но
едет в сводку и в описание PR с числом таких блоков по каждой странице: слепок
с пропусками не докладывается как полный.

## Отказы

- `snapshot publishing is disabled by notionSnapshotRepo=null` — workspace
  отключил публикацию. Env overrides не включают её обратно; для чтения
  используйте `notion` или локальный дамп `--no-push`.
- `GitHub access over gh is not ready` — нет `gh` или выбранный
  `GITHUB_TOKEN` не даёт доступ к цели. Используйте `github-login`; проверка
  идёт до обхода, чтобы не тратить время на слепок без доставки.
- `MR_STATE=unknown` — ветка запушена, но gh не ответил, есть ли у неё
  открытый PR; второй PR наугад не открывается. Проверьте ветку в UI или
  повторите позже.
- `NOTION_TOKEN is not set` — печатает `notion.sh`, лечится в корневом `.env`.
- `root '<name>' is not in notion.json` — корень добавляется записью в
  манифест, а не флагом здесь.
- `invalid notionSnapshotRepo или NOTION_SNAPSHOT_PROJECT is not set and no 'always' repository … holds
  knowledge/` — манифест не называет knowledge-репозиторий (или `packages/`
  пуст и ни у одного `always`-репозитория нет `specRoot` внутри `knowledge/`):
  исправьте явное поле `repos.json`; override допустим только без этого поля.
- `NOTION_SNAPSHOT_PROJECT is not set and … names more than one knowledge
  repository` — кандидатов несколько; выберите один переменной, а не
  молчаливым порядком в `always`.
- `MR_STATE=create-failed` — ветка запушена, но `gh pr create` отказал;
  текст отказа gh напечатан в stderr.
